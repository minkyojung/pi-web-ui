# 4단계 — 작업의 결과를 읽기

2026-09-21. 순서표(`spec-mode.md` 4절)의 4번. 브랜치 `minkyojung/spec-1c-read-and-run`, 1c의 남은 절반 위에 이어서 했다 — 읽을 재료(커밋의 트레일러)와 읽을 자리(읽기 전용 탭)를 1c가 막 깔아 놓았고, 같은 파일들을 건드리기 때문이다.

## 무엇이 되나

```
tasks.md에서 ▶ → 작업이 돈다 → 칸이 체크되고 커밋 하나가 생긴다        (3단계·1c)
  → 상태바 왼쪽 끝:  ✓ 1 task · 1 new
  → 누르면 목록:     ● 1  Add the greeting   +3 −0
  → 줄을 누르면 탭:  그 커밋이 바꾼 것 — 머리 한 덩어리, 그 아래 파일마다 diff
  → tasks.md의 끝난 줄 끝에도 [b01ccf5] — 같은 탭으로 가는 두 번째 길
```

- **계획과 기록을 나눈다.** `tasks.md`는 사람이 승인한 계획이고 그대로 계획으로 남는다. 돌린 결과의 기록은 상태바에 따로 있고, 무엇을 보고 있든 닿는다. 문서에는 끝난 줄 끝의 커밋 칩 하나만 선다.
- **새로 저장하는 것이 없다.** 아래 "상태는 어디에도 저장하지 않는다".
- **검사 줄은 에이전트의 말이고, 그렇게 보인다.** 앱이 돌린 것이 아니다.

## Kiro와 다른 점, 그리고 이유

Kiro는 끝난 작업마다 `tasks.md` 안에 "Task completed · View changes · View execution"을 붙인다(공식 문서는 "in-progress / completed로 갱신된다"까지만 말하고, 라벨은 kirodotdev/Kiro의 이슈 #3428·#1576에서 확인). 전체 diff는 채팅의 "View all changes"와 Revert다.

| | Kiro | 우리 |
|---|---|---|
| 결과가 서는 곳 | `tasks.md`의 작업마다, 문서 안 | 상태바의 목록. 문서에는 커밋 칩 하나 |
| 바뀐 것 | 채팅 세션이 기억하는 변경 | **커밋**. 작업 하나가 커밋 하나라서 `git`이 답한다 |
| 검사 | hook이 돌린 명령(Post Task Execution) 또는 모델의 말 | 지금은 모델의 말뿐, 그렇게 표시. 앱이 돌리는 검사는 6번 |
| 되돌리기 | Revert 단추 | `git revert` 하나 — 사람이 한다(3단계에서 정함) |

**이유.** 열두 작업짜리 계획에 줄마다 기록이 끼어들면 계획이 기록에 묻힌다. 그리고 Kiro에 없는 것이 우리에게 있다: 작업마다 커밋이 하나씩 남고 그 커밋이 제 주인을 말한다. 그래서 결과는 "세션이 기억하는 것"이 아니라 "저장소에 있는 것"이고, 앱을 다시 깔아도, 다른 기계에서 클론해도, 터미널에서 돌린 작업도 똑같이 보인다.

**검사를 앱이 돌리지 않는 이유.** 무엇을 돌릴지는 프로젝트마다 다르고(`npm test`, `make test`, `pytest`), Kiro도 그것을 추측하지 않는다 — 사람이 steering에 적거나(에이전트가 읽음) hook에 적는다(앱이 돌림). steering은 우리에게 이미 있다(`AGENTS.md`를 pi가 읽는다). 말로만 시키면 새는 것도 Kiro에서 확인됐다(이슈 #6518: steering의 `make test`를 무시하고 임시 vitest 설정을 만듦, "not planned"로 닫힘). hook에 해당하는 것은 6번 "앱이 돌리는 검사"이고, 올 때는 **같은 자리**에 선다 — 목록의 원이 ✓/✗가 되고 변경 탭 머리에 "앱이 돌림"이 따로 선다. 4단계의 화면은 그대로 남는다.

## 상태는 어디에도 저장하지 않는다

작업의 커밋은 제목 아래 git의 트레일러로 제 주인을 말한다(1c, `spec.ts`의 `trailersOf`):

```
Test the greeting

Spec: greeting
Task: 2
Checks: npm test — 1 passed
```

그래서 "각 작업이 무엇에 이르렀나"는 `git log` 한 번이다:

```
git log -n2000 --grep='^Task: ' --numstat -z --format=<해시·제목·시각·트레일러 셋> HEAD
```

- **HEAD에서 닿는 커밋만.** 다른 브랜치에서 한 작업은 여기서 한 것이 아니다.
- **`--grep`은 본문 어디든 맞는다.** 결과는 트레일러 둘(`Spec`, `Task`)이 실제로 있는 커밋뿐이다 — 글 속에 "Task:"라고 쓴 사람의 커밋은 아니다.
- **스펙 폴더의 파일은 "바뀐 것"에서 뺀다.** `tasks.md`의 칸은 모든 작업의 커밋에, 세 문서는 첫 작업의 커밋에 딸려 들어가는데 어느 것도 작업의 일이 아니다. `spec.ts`가 "이 실행이 뭔가 했나"를 물을 때 긋는 것과 같은 선이다. 커밋에는 있으므로 변경 탭에는 맨 아래에 접힌 채 있다.
- **다시 돌린 작업은 돌린 만큼** 있다, 오래된 것부터. 어느 것을 보일지는 화면이 정한다(마지막 것).
- 바이너리는 줄 수가 없고, 이름을 바꾼 파일은 새 이름으로 온다.

서버는 이것을 쥐고 있다가 `specs` 메시지의 `results`로 보낸다. `specs()`는 스펙 폴더에 쓰기가 있을 때마다 동기로 읽히는 자리라 매번 역사를 걷지 않는다. 다시 묻는 때: 서버가 뜰 때, 탭이 붙을 때, 턴이 끝날 때(작업의 커밋은 턴 끝에, 서버가 그 끝을 듣기 전에 만들어진다), 그리고 스펙의 파일이 바뀐 **조금 뒤** — 터미널에서 돌린 실행은 칸을 쓰고 나서 커밋하므로, 앞의 것을 보고 뒤의 것을 기다린다.

창이 기억하는 것은 하나뿐이고 저장소의 것이 아니다: **어디까지 봤나**. 스펙별로 마지막에 본 커밋을 localStorage에 둔다(`seenResults.ts`). 개수가 아니라 커밋인 이유는 아래 "정한 것".

## 파일별로 한 일

### `specResults.ts` (새 파일)

`taskResults(root)` — 위의 `git log` 한 번과 그 읽기(`parseResults`). 읽기를 묻기와 떼어 글자로 시험한다. Octave의 것은 스펙 폴더의 자리뿐이다(`specTasks.ts`처럼).

### `commitRead.ts` (새 파일)

`readCommit(root, name)` — 커밋 하나: 제목·시각·트레일러, 그리고 파일마다 **전과 후의 본문 전체**와 git이 센 줄 수.

- **patch가 아니라 전/후를 통째로 주는 이유.** 창은 편집기 자신의 merge view로 차이를 그리는데 그것은 두 글을 원한다. 그래야 안 바뀐 줄을 접었다가 그 자리에서 펼 수 있다 — patch에는 자기가 고른 줄밖에 없다.
- **그릴 수 없는 것은 이유를 말한다.** 바이너리(디스크의 파일을 판정하는 `vault.ts`의 규칙 그대로: 앞 8,000바이트의 NUL)와, 한쪽이라도 `CODE_MAX`를 넘는 파일. 잘라서 비교하면 없는 차이가 생기므로 자르지 않고 보이지 않는다.
- **줄 수는 git의 것.** 처음엔 창이 두 글에서 대충 세게 짰다가, 목록의 숫자(numstat)와 어긋날 수 있어 서버가 `diff-tree --numstat`을 그대로 주게 바꿨다.
- **커밋의 이름은 16진 해시뿐이다.** 이름이 창에서 오므로 브랜치도, `HEAD~1`도, 대시로 시작하는 것도 git에 넘기지 않는다(`isCommitName`). 첫 부모와 비교하고, 부모가 없으면 전부 새 파일이다. `.pi/`는 커밋에 있어도 내주지 않는다.

### `protocol.ts` · `server.ts`

`SpecInfo.results`, 그리고 `open_commit` → `commit` | `commit_gone`. 묻기만 하고 지켜보지 않는다 — 커밋은 바뀌지 않는다.

### 창

- **`pages.ts`** — `octave://commit/<해시>`가 새 종류의 페이지다. 주소라서 탭·뒤로 가기·해시가 새로 배울 것이 없다. 짧은 해시도 된다.
- **`Commit.tsx`** — 머리 한 덩어리(작업 칩·제목·커밋 칩·파일 수·+/−·`agent: …`·스펙·시각) 아래 파일 블록이 **세로로 쌓인다**. 이름 줄 뒤에 하나씩 숨기지 않는다: 작업의 커밋은 파일 몇 개이고, "이 작업이 뭘 했나"는 한 번 스크롤해서 답이 나와야 한다. 블록마다 CodeMirror `unifiedMergeView`, 읽기 전용, 그 파일의 문법과 코드 탭과 같은 색(`codeLook.ts`로 옮겨 둘이 나눠 쓴다). 바뀐 곳 위아래 3줄만 남기고 접는다(`collapseUnchanged` — git과 GitHub의 맥락 3줄), 접힌 띠는 누르면 그 자리에서 펴진다. 전부 새것이거나 전부 지운 파일은 줄 색만 — 모든 낱말이 바뀌었으니 낱말마다 칠하는 것은 아무 말도 아니다. 파일 이름은 그 파일을 지금 모습으로 연다.
- **`resultsList.ts`** — 서버의 목록을 읽는 용으로 접는 순수 함수: 작업마다 한 줄(마지막 실행), 한 순서대로, 합계, 안 본 개수.
- **`TaskResults.tsx`** — 상태바 노트 절반의 맨 앞. `Popover` 안에 `Command`(⌘P·크럼 메뉴와 같은 조합 — 화살표·Enter·번호나 낱말로 좁히기가 따라온다; 여섯 줄을 넘으면 검색칸). 상태바의 다른 팝업은 `HoverCard`지만 이것은 안에서 누르므로 `Popover`다. 탭 줄 맨 앞의 스펙 버튼이 말하는 스펙을 말한다(`speaksFor`) — 둘이 다른 스펙을 가리킬 수 없다.
- **`features/taskCommit.ts`** — `tasks.md`의 끝난 잎 작업 줄 끝의 커밋 칩. ▶(`taskStart.ts`)와 같은 방식의 위젯이고 값은 Facet으로 받는다. 어느 커밋인지는 목록과 같은 `listOf`에서 — 두 곳이 어긋나지 않는다.

## 정한 것

- **계획과 기록을 나눈다**(2026-09-21, 사용자 제안). 처음 안은 끝난 줄 아래에 접히는 한 줄(해시·바뀐 양·검사·`[diff]`)이었다 — `task-runs.md`에 "붙을 모습"으로 적혀 있던 것. 상태바 버튼 → 목록 → 별도 탭으로 바꿨다. 문서에는 칩 하나만.
- **상태바 버튼이 말하는 것은 둘뿐: 몇 개 끝났나, 그중 몇 개를 안 봤나.** 후보를 질문별로 놓고 골랐다 — 바뀐 줄 수는 느낌일 뿐이고(목록에 있다), 마지막 시각은 에이전트 절반이 이미 말하고, 커밋 수는 작업 수를 두 번 말하는 것이다(작업이 곧 커밋). "안 본 것"만이 사람이 다음에 할 일을 바꾼다: 큐를 돌려 놓고 돌아왔을 때의 질문이 그것이다. 이 상태바에는 같은 생각이 이미 있다 — 링이 "결과를 아직 못 본 실행"을 표시한다(`working.ts`).
- **본 것은 개수가 아니라 마지막 본 커밋으로 기억한다.** 개수는 그 밑의 역사가 바뀌는 순간 틀린다(브랜치 전환, amend). 그 커밋이 목록에 없으면 아무것도 안 본 것 — 틀려도 안전한 쪽이다. 목록을 여는 것이 보는 것이고, 새것 표시는 목록이 떠 있는 동안 남는다.
- **목록은 작업마다 한 줄**(2026-09-21, 사용자 지적). 처음엔 두 줄에 일곱 가지였다. 목록의 질문은 "어느 것을 열까" 하나이고 그것에 필요한 것은 넷이다: 어느 작업, 검사했나, 얼마나, 봤나. 해시와 시각은 참조라서 줄의 title과 변경 탭 머리에 있다.
- **검사는 왼쪽의 원이다.** 채운 원 = 에이전트가 검사했다고 함(title에 그 말), 빈 호박색 원 = 아무것도 안 함 — 열어 볼 그 작업. **✓가 아닌 이유:** 초록 ✓는 "돌렸고 통과했다"로 굳어 있는데 이것은 에이전트의 말이다. 앱이 직접 돌리게 되면 같은 자리에 ✓와 ✗가 선다.
- **안 본 것은 굵게.** 안 읽은 메일과 같아 배울 것이 없고, 왼쪽 표식 하나가 한 가지만 뜻하게 된다(처음엔 그 점이 "새것"이었다).
- **다시 돌린 작업의 `×2`는 줄에서 뺐다.** 한 번, 그리고 길게 설명하고도 이해되지 않았다 — 그것으로 정해졌다. 몇 번 만에 됐는지는 목록을 여는 이유가 아니다. 줄의 title에만 있다.
- **파일은 한 탭에 세로로 쌓는다.** 위 `Commit.tsx`.
- **칩은 그리고, 쓰지 않는다.** `tasks.md`의 지문은 그 글자에 걸려 있다(`specApproval.ts`) — 해시를 적으면 승인이 풀린다. 커밋으로 끝난 작업에만: 손으로 체크한 칸은 아무것으로도 끝나지 않았고, 지어낼 것이 없다. 묶음에는 제 커밋이 없다.
- **칩은 `inline-block`이다.** 끝난 줄은 취소선인데, 취소선은 조상이 인라인 자식 위로 긋는 것이라 자식이 끌 수 없다. inline-block 위로는 긋지 않는다. **outline이 아니라 채움(secondary):** 어두운 테마의 `--border`는 흰색 5%라 그 색의 테두리는 칩이 아니라 글자로 읽힌다.
- **작업이 아닌 커밋은 목록에 없다.** 채팅으로 고친 것, 사람이 직접 한 커밋, 커밋 안 된 변경. 목록의 질문이 "각 작업이 뭘 했나"이기 때문이다. 작업 도중에 에이전트가 덤으로 고친 것은 그 작업의 커밋에 들어가므로 변경 탭에 보인다 — 다만 왜 그랬는지는 그 세션의 대화에만 있다.

## 실창에서 본 것 (2026-09-21, gpt-5.6-luna, thinking minimal)

`.context/taskrun.mjs` — 격리한 사용자 데이터·`APP_DIR`·깨끗한 저장소에 실제 앱을 띄우고, 승인된 스펙의 작업 둘을 `Run 1, 2`로 실모델에 맡긴 뒤 결과 화면을 차례로 눌렀다. **HOME은 실제 것**이다: 로그인이 OAuth라서 임시 HOME에 복사하면 토큰 갱신이 사본에서 일어나 원본이 풀릴 수 있다. pi가 실제 HOME 아래에 남긴 그 폴더의 세션은 끝에 지운다.

| 본 것 | |
|---|---|
| 돌리기 전에는 상태바에 결과 버튼이 없다 | ok |
| 첫 커밋 직후 `1 task · 1 new`, 둘째 뒤 `2 tasks · 2 new` — **실제 서버가 커밋을 알아채고 git에서 읽었다** | ok |
| 끝난 줄의 칩 = 실제 커밋, 파일에는 해시 없음, 승인 유지 | ok |
| 목록 두 줄, 둘 다 굵게, 원의 title = 에이전트가 실제로 쓴 `Checks:` 문장 | ok |
| 변경 탭 머리의 숫자 = `git show --numstat` | ok |
| 첫 작업의 커밋: 작업 파일 1개로 세고, 딸려 간 문서 넷은 "Spec files (4)"에 접혀 있음 | ok |
| 본 뒤 `2 tasks`, 창을 다시 로드해도 그대로 | ok |

**테스트가 파랬는데 실창에서만 보인 것 하나** (1c의 실행 쪽, 이 검증의 첫 회에서): 저장소가 `.pi`를 무시하면 — 앱의 폴더이니 대부분 그럴 것이다 — `git add -A -- . ':(exclude).pi'`가 "무시된 경로를 지정했다"며 exit 1이었다. 작업은 칸이 체크된 채 커밋되지 않았고 큐는 거기서 멈췄다("1 was not committed, so 2 was not started" — 그래서 보였다). 시험 저장소는 전부 `.pi`를 무시하지 않았다. 전부 담은 뒤 앱의 폴더만 도로 내린다(`a2053cdf`).

이 검증이 말하지 못하는 것: 실제 마우스 클릭(스크립트는 DOM을 직접 누른다 — 창 끌기 영역과 겹쳐 클릭만 죽는 문제는 못 잡는다), 파일 수십 개짜리 큰 커밋, 창을 완전히 껐다 켜기(같은 창의 다시 로드까지만).

## 이번에 안 한 것

- **작업의 대화 열기.** Kiro의 "View execution". 지금 커밋에는 어느 세션이 했는지가 없다 — 트레일러에 `Session:` 한 줄을 더하면 그 뒤의 커밋부터 이어진다.
- ~~**앱이 돌리는 검사.**~~ 첫 단계는 함(2026-09-22): 작업 턴이 끝나면 코드가 그 작업의 `_Done when:` 줄에서 첫 백틱의 명령을 꺼내 워크스페이스에서 돌리고(`/bin/bash -lc`, 10분), 어떻게 끝났든 커밋하며 `Verified: <명령> — exit N` 트레일러를 `Checks:` 옆에 남긴다. 목록의 원은 그 줄이 있으면 ✓(초록)·✗(빨강)가 된다 — 에이전트의 말(원)과 앱이 확인한 것(✓/✗)이 구별된다. 실패해도 커밋하는 이유: 되돌리는 단위가 커밋이고, 실패한 시도도 기록이다; 다시 고치게 하는 것은 다음 단계. 출력은 남기지 않는다(커밋은 끝난 방식만, 출력이 필요하면 다시 돌린다). 저장소 설정 파일은 1h에서 함(2026-09-22): `.octave/config.toml`의 `[[scripts.check]]`가 작업의 `_Done when:` 앞에 순서대로 돌고, 검사마다 `Verified:` 한 줄, 출력 꼬리는 `.pi/runs/<작업>/<이름>.log`, exit 2는 커밋을 막는다.
- **브랜치 전체가 바꾼 것**(`main..HEAD`). PR 앞에서 필요해질 화면이고 같은 부품(`Commit.tsx`의 파일 블록)으로 선다. 순서표에 아직 자리가 없다.
- **지운 줄의 문법 색.** 문법은 나중에 로드되는데 merge view의 지운 줄 위젯은 그때 다시 그려지지 않는다. 읽는 데 지장은 없다.
- **큰 커밋 대비.** 블록을 접어 두고 열 때 그리기. 파일은 200개까지 준다(`FILES_MAX`).
