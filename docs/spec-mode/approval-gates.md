# 2단계 — 승인 관문

> **2026-09-23:** 관문은 둘이 됐다 — `tasks.md`는 승인하지 않는다(`spec-mode.md` 결정 목록). 설계가 승인되면 에이전트가 작업 목록을 쓰고 멈추고, 사람은 읽고 `/spec-run`한다. 아래 흐름의 마지막 `/spec-approve` 한 줄은 그래서 없다.

2026-09-19 계획. 순서표(`spec-mode.md` 4절)의 2번. Kiro가 어떻게 하는지는 `kiro-how-it-works.md` 2~4·7절.

## 무엇이 되나

```
/spec 이메일 로그인 추가
  → requirements.md를 쓰고 멈춤   "requirements.md가 승인을 기다립니다 — 괜찮으면 /spec-approve"
  → (원하는 만큼 대화하고, 고쳐 달라고 하고, 직접 고친다)
  → /spec-approve (터미널과 Octave의 메시지 상자 모두)
  → design.md를 쓰고 멈춤
  → /spec-approve → tasks.md를 쓰고 멈춤
  → /spec-approve → "스펙이 준비됐습니다." 끝 (작업 실행은 3단계)
```

- **묻지 않는다.** 에이전트는 문서를 쓰고 멈출 뿐이다. 창이 뜨지 않는다. 승인은 사람이 준비됐을 때 누른다.
- **승인 없이는 다음 문서를 못 쓴다.** 코드가 막는다.
- **되돌아가기는 새 장치가 아니다.** 승인한 문서를 누가 고치든(사람이든 에이전트든) 그 문서와 그 뒤 문서의 승인이 풀린다. 다시 승인하면 에이전트가 다음 문서를 새 내용에 맞춰 점검한다. 바꿀 것이 없으면 그렇다고 말하고, 있으면 고친다. 그러고 나서 다시 멈춘다. 처음 만들 때와 같은 사슬을 한 칸 위에서 다시 탄다.

## Kiro와 다른 점 두 가지, 그리고 이유

| | Kiro (공개 프롬프트) | 우리 |
|---|---|---|
| 승인을 묻는 쪽 | 문서를 고칠 때마다 모델이 `userInput` 도구로 묻는다 | 묻지 않는다. 사람이 준비됐을 때 명령(`/spec-approve`)으로 한다 |
| 승인인지 가리는 쪽 | 모델이 "yes / looks good"을 읽고 판단한다 | 명령을 쳤다는 사실. 코드가 안다 |
| 순서를 지키게 하는 것 | 프롬프트의 MUST | 코드가 다음 문서 쓰기를 거절한다 |
| 앞 문서를 고친 뒤 | 사람이 Refine / Sync Files를 누른다 | 승인이 저절로 풀리고, 재승인하면 다음 문서를 점검한다 |

**이유:** 고칠 때마다 뜨는 질문은 더 다듬고 싶은 사람을 방해한다. Octave의 질문 창은 메시지 상자 자리에 뜨기 때문이다. 또 승인을 모델이 판단하면 "좋아, 근데 3번은 빼 줘" 같은 답이 샌다. 1b에서 모델이 `.git`을 손으로 쓴 일처럼, 말로만 막은 것은 새기 쉽다.

## 상태: 승인 기록 하나로 안다

`.octave/specs/{이름}/approvals.json`

```json
{ "requirements.md": ["<requirements의 sha256>"],
  "design.md":       ["<requirements의 sha256>", "<design의 sha256>"] }
```

- 승인할 때 **그 문서와 앞 문서들의 지문**(sha256)을 적는다.
- **승인됨** = 적힌 지문이 지금 파일들과 모두 같다. 그래서 문서를 고치면 그 문서와 그 뒤 문서의 승인이 저절로 풀린다. 따로 풀어 주는 코드가 없다.
- **승인 대기** = 파일이 있고, 앞 문서는 모두 승인됐고, 이 문서만 승인이 없다.
- **순수 함수 하나**(`specState`)가 이것을 계산한다. 명령·막는 장치(나중에는 화면도)가 모두 이 함수를 부른다. 따로 저장하는 상태는 없다.
- 폴더 안에 두는 이유: git에 올라가 PR에서 무엇이 승인됐는지 보이고, 세션이 바뀌어도 남는다. 3단계의 "Start task"도 이 기록을 본다. `.json`이라 `isSpec`에 걸리지 않으므로 탭이나 노트 목록에 끼지 않는다.
- 공백 하나를 고쳐도 승인이 풀린다. 일부러 이렇게 한다. 느슨하게 비교하는 규칙은 필요해질 때 더한다.

## 파일별로 바꾸는 것

### `spec.ts` — 핵심. 터미널 pi에서도 전부 돈다

1. **`specState(cwd, name)`** (`specApproval.ts`) — 위의 함수. 앞에서부터 몇 개가 승인됐는지와, 지금 승인을 기다리는 문서를 준다.
2. **`/spec-approve` 명령** — `/spec approve`가 아닌 이유: `/spec` 뒤의 글은 만들 것을 적는 한 줄이라, "approve로 시작하는 한 줄"과 구별되지 않는다. `/approve`가 아닌 이유: 다른 확장의 명령과 겹치지 않게, 그리고 `/spec`을 치면 목록에 나란히 보이게.
   - 에이전트가 일하는 중이면 알리기만 한다(`/spec`과 같음).
   - 대기 중인 스펙이 하나면 그것을 승인한다. 여럿이면 `/spec-approve {이름}`을 요구한다. 없으면 그렇다고 알린다.
   - 승인을 기록한다.
   - 마지막 문서(`tasks.md`)였으면 "스펙이 준비됐습니다"라고 알리고 끝낸다. 턴은 시작하지 않는다.
   - 아니면 `/spec`과 같은 방식으로 턴을 시작한다. 사람의 메시지로는 `/spec-approve`만 남고, 지시문은 숨긴 메시지로 모델에게만 간다.
     - **다음 문서가 아직 없을 때:** 쓰라는 지시와 Kiro의 형식.
     - **다음 문서가 이미 있을 때(되돌아간 경우):** "앞 문서가 바뀌었다. 둘을 읽고, 맞지 않는 곳만 고쳐라. 바꿀 것이 없으면 그렇다고 말하라. 그러고 나서 멈춰라."
3. **설계·작업 지시문** — Kiro 프롬프트의 design 절(6개 절, Mermaid, 이 단계에서 코드를 읽고 조사)과 tasks 절(코드 생성 LLM에게 줄 프롬프트로, 두 단계 체크박스, `_Requirements: x.y_`, 코딩 작업만)을 그대로 옮긴다. 언어 규칙은 requirements와 같다. 두 지시문 모두 "빈 곳을 찾으면 고치지 말고 앞 문서로 돌아가자고 말하라"를 넣는다(Kiro의 MUST offer to return).
4. **막는 장치** — `pi.on("tool_call")`로, `edit`·`write`가 스펙 문서를 쓰려 할 때 **앞 문서가 모두 승인되지 않았으면 거절**한다. 이유 문구는 모델이 알아듣게: "requirements.md가 승인되지 않아 design.md를 쓸 수 없다. 사람이 승인하면 쓸 수 있다." 앞 문서를 고치는 것(되돌아가기)은 막지 않는다. guard.ts가 아니라 여기에 두는 이유는 터미널에서도 돌아야 해서다.
5. **`/spec`의 지시문 끝줄** — "승인하라고 묻지 말고, 읽고 고칠 것을 말한 뒤 멈춰라." 승인 방법은 모델이 아니라 코드가 알린다(6번).
6. **턴이 끝날 때(`agent_settled`)** — 이 턴에 어떤 문서가 새로 **대기 상태가 됐을 때만** 한 번 알린다: "requirements.md가 승인을 기다립니다. 읽어 보고, 괜찮으면 /spec-approve." Octave에서는 이 알림이 대화에 한 줄로 남는다(extensionUI.ts). 대기 중이라고 매 턴 알리지 않는다. 자꾸 뜨는 것이 이번에 피하려는 바로 그것이다. 1b의 브랜치 이름 바꾸기는 그대로 둔다.

### 화면은 이번에 없다 (1c로) — **1c에서 붙음(2026-09-20)**

Octave의 메시지 상자에서도 `/spec-approve`는 그대로 먹힌다(pi 명령 목록에 뜬다). 막대와 그것에 필요한 서버 알림은 1c에서 스펙 문서 열기와 같이 한다.

붙은 모습(1c): 서버가 `specs` 메시지로 스펙마다 `{승인 수, 기다리는 문서, 그 문서가 쓰인 시각, 써진 문서들}`을 보내고(`protocol.ts`·`server.ts`, `watcher.ts`가 `approvals.json`까지 지켜본다), 창은 그것만 읽는다. 두 자리에서 승인한다 — **탭 줄 맨 앞의 스펙 버튼**(스펙 이름 + 기다리는 것, 메뉴에 세 문서와 상태, 대기 중이면 `Approve`)과 **기다리는 문서 위의 한 줄 막대**. 둘 다 사람이 치는 것과 같은 명령을 보낼 뿐이다(`web/src/specApprove.ts`) — 화면은 승인을 판단하지 않고, 기록은 여전히 `spec.ts` 뒤의 코드가 쓴다. 명령은 메시지와 달리 큐에 들어가지 않으므로(에이전트가 일하는 중이면 거절된다) 그때는 버튼이 비활성이고 이유를 말한다.

## 실모델로 본 것 (2026-09-19, gpt-5.6-luna, thinking minimal)

두 번 돌렸다. 스크립트는 `.context/spec-chain-run.mjs`(Octave 서버)와 `.context/spec-cli-run.mjs`(터미널 `pi --mode rpc -e spec.ts`)다.

- **말로 한 승인은 승인이 아니다.** 설계대로다. 처음에는 한 번 헛썼다: 에이전트는 그 턴에 스펙이 기다리는 중인지 모르고 설계를 통째로 쓴 뒤에야 거절당했다(Octave에서 35.6초). 그래서 스펙이 기다리는 동안 매 턴 사람의 메시지 옆에 숨긴 한 줄("이 메시지를 보낼 때 requirements.md가 승인을 기다리고 있었다, 사람이 /spec-approve로 승인한다")을 붙인다. pi의 `before_agent_start`로, `guard.ts`가 열린 노트를 알리는 방식과 같다. 시스템 프롬프트가 아닌 이유는 캐시다. 다시 돌리니 **3.0초**, 도구 호출 없이 "먼저 `/spec-approve`로 승인해 주세요"라고 답했다(`.context/spec-waiting-run/`).
- **빈 곳은 고치지 않고 말했다.** 작업 목록을 쓰던 모델이 "설계에 세션 추상화가 없어 보완이 필요하다"고 말하고, 설계는 건드리지 않았다.
- **터미널에는 셸이 있다.** 모델은 `mkdir`에 bash를 썼다. 막는 장치는 edit·write만 보므로, 셸로 문서를 쓰면 막지 못한다(이번에 안 하는 것).
- 1b부터 있던 것: 한국어 수용 기준에서 SHALL이 가끔 문장 끝에 온다. 이번 일과는 무관하다.
