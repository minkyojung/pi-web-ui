# Kiro는 어떻게 동작하는가 — 순서대로

2026-09-18 조사. 우리 제품 이야기는 없다. Kiro만.
근거 두 종류: **[문서]** kiro.dev 공식 문서(2026-09 현재), **[프롬프트]** 커뮤니티가 추출해 공개한 Kiro 스펙 에이전트의 시스템 프롬프트(2025 프리뷰 시절; 출처는 맨 아래). 프롬프트는 옛 판이므로 문서와 다르면 문서가 맞다. 직접 돌려 확인한 것은 아직 없다.

## 0. 깔려 있는 것

- 스펙은 저장소 안의 파일이다: `.kiro/specs/{기능-이름}/` 아래 `requirements.md`(버그면 `bugfix.md`) · `design.md` · `tasks.md`. 코드와 같이 git에 올린다. [문서]
- 기능 이름은 에이전트가 사용자의 한 줄에서 kebab-case로 짓는다(`user-authentication`). [프롬프트]
- 배경 문서(steering): `.kiro/steering/`의 `product.md` · `tech.md` · `structure.md`가 모든 대화에 자동으로 들어간다. [문서]
- 한 저장소에 스펙 여러 개. 기능별로 나눈다. [문서]

## 1. 시작

- 사용자가 채팅에 한 줄을 쓰거나("이메일 인증과 비밀번호 재설정 스펙이 필요해"), Kiro 패널에서 새 스펙을 만든다. [문서]
- 종류를 고른다: **Feature**(요구사항 먼저 / 설계 먼저) 또는 **Bugfix**. 시작한 뒤에는 못 바꾼다 — 새 스펙을 만든다. [문서]
- **Quick Spec**: 세 문서를 승인 없이 한 번에 만든다. 잘 아는 기능·시제품용. [문서]

## 2. 요구사항 (`requirements.md`)

1. 에이전트는 **질문부터 하지 않는다.** 한 줄만 가지고 초안을 먼저 쓴다. 이 단계에서는 코드 탐색에 힘을 쓰지 않는다. [프롬프트]
2. 형식은 고정: 소개 → 번호 붙은 요구사항들. 요구사항 하나 = **사용자 이야기**("As a [역할], I want [기능], so that [이득]") + 번호 붙은 **수용 기준**(EARS: `WHEN [사건] THEN [시스템] SHALL [반응]`, `IF [전제] THEN …`). 예외·에러 상황도 넣는다. [프롬프트][문서]
3. 다 쓰면 **정해진 질문으로 멈춘다**: "Do the requirements look good? If so, we can move on to the design." — 일반 채팅이 아니라 `userInput` 도구를 `spec-requirements-review`라는 이유로 부른다. UI가 이것을 받아 승인 단추를 그린다. [프롬프트]
4. 사용자가 고쳐 달라고 하면 고치고 **다시 같은 질문으로 멈춘다.** "yes/approved/looks good" 같은 분명한 승인 전에는 다음으로 가지 않는다. [프롬프트]
5. 에이전트는 부족해 보이는 곳을 짚어 줄 수 있고(SHOULD), 선택지를 내놓을 수 있다(MAY) — 의무는 아니다. [프롬프트]

## 3. 설계 (`design.md`)

1. 요구사항이 승인된 뒤에만 시작. **이 단계에서 조사한다**: 코드베이스와 필요한 자료를 읽고, 찾은 것을 대화에 요약한다. 조사 파일을 따로 만들지 않는다. [프롬프트]
2. 절이 고정: Overview · Architecture · Components and Interfaces · Data Models · Error Handling · Testing Strategy. 그림은 Mermaid. 결정과 그 이유를 적는다. [프롬프트]
3. (2025-11 이후) 요구사항에서 **"언제나 성립해야 하는 속성"**을 뽑아 설계에 넣는다. 속성마다 어느 요구사항에서 왔는지가 이어져 있다. 검사 가능한 것만. [문서]
4. 같은 방식으로 멈춘다: "Does the design look good? …" (`spec-design-review`). 고치면 다시 묻는다. 설계하다 요구사항의 구멍을 찾으면 **요구사항으로 돌아가자고 제안해야 한다.** [프롬프트]
5. 문서는 미리보기로 열린다. [문서]

**설계 먼저** 흐름은 2와 3의 순서가 뒤집힌다: 설계(High/Low level 선택)를 승인받고, 그 설계로 *가능한* 요구사항을 끌어낸다. [문서]

## 4. 작업 목록 (`tasks.md`)

1. 설계가 승인된 뒤에만. 에이전트에게 주어지는 지시의 핵심: *"설계를 코드 생성 LLM에게 줄 프롬프트의 연속으로 바꿔라. 테스트 주도로, 조금씩, 앞 단계 위에 쌓고, 마지막은 전부 잇는 것으로. 어디에도 안 이어진 코드가 없게."* [프롬프트]
2. 형식 고정: 번호 붙은 체크박스, **최대 두 단계**(1, 1.1). 항목마다 할 일 설명(하위 글머리) + `_Requirements: 1.2, 3.3_` — 어느 수용 기준을 위한 것인지. 모든 요구사항이 어느 작업엔가 걸려야 한다. [프롬프트]
   ```
   - [ ] 2. Implement data models and validation
   - [ ] 2.1 Create core data model interfaces and types
     - Write TypeScript interfaces for all data models
     - _Requirements: 2.1, 3.3, 1.2_
   ```
3. **코드로 할 수 있는 일만.** 배포, 사용자 테스트, 성능 측정, 문서 작성, "앱을 직접 돌려 보기"는 작업으로 넣지 않는다(자동화된 테스트를 쓰는 것은 된다). [프롬프트]
4. 선택 작업은 `*`로 표시(테스트 작업이 흔히 그렇다). 속성 테스트 작업도 기본은 선택. [문서]
5. 세 번째 멈춤: "Do the tasks look good?" (`spec-tasks-review`). 승인되면 **스펙 만들기 흐름은 거기서 끝난다.** 구현은 별개의 흐름이다 — 에이전트는 여기서 코드를 쓰면 안 된다. [프롬프트]

## 5. 실행

- `tasks.md`를 열면 최상위 작업 위에 **"Start task"**가 뜬다. 누르면 그 작업 하나로 세션이 돈다. 진행 중/완료가 문서에 표시된다. [문서]
- 실행 에이전트의 규칙 [프롬프트]:
  1. 시작 전에 **세 문서를 반드시 다 읽는다.**
  2. 하위 작업이 있으면 하위부터.
  3. **한 번에 작업 하나.** 다른 작업의 기능을 만들지 않는다.
  4. 작업에 적힌 요구사항에 비추어 자기 구현을 확인한다.
  5. 끝나면 **멈춘다.** 다음 작업으로 알아서 넘어가지 않는다.
- (이후 추가) **"Run all tasks"**: 의존 관계를 그래프로 만들어, 서로 독립인 작업은 한 물결(wave)로 동시에, 물결끼리는 차례로. [문서]
- 실행 모드 [문서]: **Autopilot**(기본) — 끝까지 알아서, 사람은 전체 diff를 보고 통째로 되돌릴 수 있음. **Supervised** — 파일을 고친 턴마다 멈추고, 사람이 조각(hunk)마다 받거나 거절.
- **IDE는 커밋하지 않는다.** 내 작업 폴더를 바로 고친다. 되돌리기는 체크포인트(에이전트의 파일 도구가 쓴 것만 스냅샷; bash·MCP가 바꾼 파일은 추적 못 함). [문서]
- "Task completed" 표시는 코드가 맞다는 보증이 아니다 — 문서가 직접 그렇게 말한다. [문서]

## 6. 검증

- 작업 실행 에이전트의 자기 확인(위 4번). [프롬프트]
- 작업 목록 자체가 테스트 주도로 짜인다 — 테스트 작성이 작업에 들어 있다. [프롬프트]
- **속성 기반 테스트**: 요구사항에서 뽑은 속성을 무작위 입력 수백~수천 개로 두드린다. 깨지면 가장 작은 반례로 줄여 보여 주고, **코드·스펙·테스트 중 무엇을 고칠지 사람이 고른다.** [문서]
- **Hooks**: 파일 저장/생성/삭제, 도구 사용 전후, 에이전트 정지, **작업 실행 전후**에 셸 명령이나 에이전트 지시를 자동 실행. `.kiro/hooks/`에 JSON. [문서]

## 7. 고칠 때

- 요구사항을 고친 뒤 `design.md`에서 **Refine** → 설계와 작업이 따라 갱신된다. 작업 목록은 sync로 다시 만든다. [문서]
- 채팅에서 `#spec`으로 스펙을 맥락에 넣어 묻거나 고친다. [문서]
- 들어가는 문은 넷: 새로 만들기 / 세 문서 중 하나를 갱신 / 작업 실행. [프롬프트의 상태도]

## 8. 버그 스펙 (`bugfix.md`)

세 칸: 지금 동작(`WHEN … THEN the system [틀린 동작]`) · 올바른 동작(`… SHALL …`) · **그대로여야 하는 동작**(`… SHALL CONTINUE TO …`). 검사 셋: 고치기 전 코드에서 재현되는가, 고친 뒤 사라졌는가, 그대로여야 할 것이 그대로인가. [문서]

## 9. 같은 회사의 다른 두 실행기 (IDE 밖)

- **Kiro Crew Task Runner**(오픈소스, 2026-08): 스펙 하나 = 브랜치 `kirocrew/task/{id}` + `git worktree add` 하나. 단계마다 새 세션 → 테스트 → 통과하면 커밋 → 별도 세션의 검토자가 `git diff HEAD~1`을 읽음 → 떨어지면 `git reset --hard HEAD~1` 후 재시도(3회) → 재계획(2회) → 전체 50단계 상한. 같은 에러 3번이면 정지. 위험 단계는 `force_approval`. 동시 3. 푸시·머지 없음. [문서]
- **자율 에이전트**(클라우드): 저장소를 샌드박스에 clone → 사용자가 청하면 브랜치·커밋·푸시·PR → PR 댓글에 답하며 다시 푸시. 머지는 사람. [문서]

## 10. 한 장으로

```
한 줄 ─▶ requirements.md ─(승인)─▶ design.md ─(승인)─▶ tasks.md ─(승인)─▶ 끝
            ▲  고쳐 달라 │            ▲  고쳐 달라 │         ▲ 고쳐 달라 │
            └───────────┘            └───────────┘         └──────────┘
                     (구멍을 찾으면 앞 문서로 되돌아감)

tasks.md ─ Start task ─▶ 세 문서 읽기 ─▶ 작업 하나 ─▶ 자기 확인 ─▶ 멈춤 ─▶ 사람이 봄
```

Kiro의 몸통은 세 가지다: **① 고정된 문서 형식 셋 ② "분명한 승인 전에는 다음으로 안 간다"는 상태 기계(승인 질문은 전용 도구 호출) ③ "세 문서를 읽고, 작업 하나만 하고, 멈춘다"는 실행 규칙.** 나머지(물결, 속성 테스트, hooks, Crew)는 그 위에 나중에 얹힌 것이다.

## 아직 모르는 것 (직접 돌려 확인할 것)

- 지금 판의 프롬프트가 2025 프리뷰와 얼마나 다른가(속성, 선택 작업 `*`, 물결).
- "Start task"가 `tasks.md`의 어느 모양을 작업으로 알아보는가 — GitHub 이슈 #2476 · #3810 · #9405가 전부 여기서 깨졌다.
- 작업 상태(진행 중)가 파일에 어떻게 적히는가(`[-]`인지, 파일 밖인지).
- Run all tasks의 동시 작업들이 같은 폴더를 어떻게 나눠 쓰는가.
