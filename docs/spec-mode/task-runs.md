# 3단계 — 작업 실행

2026-09-20 계획. 순서표(`spec-mode.md` 4절)의 3번. Kiro가 어떻게 하는지는
`kiro-how-it-works.md` 4·5·9절. 앞 단계는 [`approval-gates.md`](approval-gates.md).

## 무엇이 되나

```
/spec-approve  → "스펙이 준비됐습니다."   (2단계까지)

/spec-run
  → 새 세션이 세 문서를 읽고, tasks.md의 다음 작업 하나만 하고 멈춤
  → 코드가 그 작업의 칸을 체크하고 커밋 하나를 남김
  → "2.1 끝 — 커밋 a1b2c3d. 다음은 2.2 — /spec-run"
/spec-run 2.3        (작업을 골라서)
/spec-run email-auth 2.3   (스펙이 여럿일 때)
```

- **작업 하나 = 세션 하나 = 커밋 하나.** 작업마다 새 대화를 여는 것은 Kiro의 "Start task"와
  같다. 열두 작업을 한 대화에서 하면 문맥이 넘친다.
- **폴더는 하나.** 작업은 앞 작업 위에 쌓이게 짜이므로(Kiro의 tasks 지시문: "each prompt
  builds on the previous prompts… no hanging or orphaned code") 작업마다 worktree를
  나누지 않는다. 스펙 하나 = 브랜치 = worktree = PR, 이것이 `spec-mode.md` 6절의 단위다.
  서로 독립인 작업을 동시에 돌리는 것(Run all)은 6번 이후다.
- **승인 없이는 시작하지 않는다.** 세 문서가 모두 승인된 스펙만 돈다.

## Kiro와 다른 점 둘, 그리고 이유

| | Kiro | 우리 |
|---|---|---|
| 끝난 표시 | 모델이 `tasks.md`를 고친다 | **코드가 고친다** |
| 커밋 | IDE는 커밋하지 않는다(작업 폴더를 바로 고치고, 되돌리기는 체크포인트). Crew Task Runner는 단계마다 커밋한다 | **코드가 작업마다 커밋 하나** |

**이유:** 모델이 못 해서가 아니라, 사람이 어느 칸에 있느냐에 따라 되기도 안 되기도 하면
안 되기 때문이다 — Plan에는 셸이 아예 없고 Execution에는 있다(`toolModes.ts`). 작업이
커밋으로 남는지가 모드에 달려 있으면 그건 단위가 아니다. 1b에서 `git branch -m` 대신
`.git/HEAD`를 손으로 쓴 일도 있었고, 거기서 "판단은 모델이, 조작은 코드가"를 정했다. 끝난
표시도 같은 쪽에 둔다 — 체크와 커밋이 갈라지면 어긋난 쪽이 무엇인지 알 길이 없다.

## 진척은 승인을 풀지 않는다

`approvals.json`은 문서의 sha256을 들고 있다. 작업을 하나 끝내고 `- [ ]`를 `- [x]`로 바꾸면
지문이 달라져 **`tasks.md`의 승인이 저절로 풀린다** — 작업마다 재승인을 요구하게 된다.
2단계가 "느슨한 비교는 필요해질 때"라고 미뤄 둔 것이 여기서 필요해졌다.

그래서 `tasks.md`의 지문은 **체크 칸을 빈 칸으로 돌려놓은 글**에서 뜬다. 사람이 승인한 것은
계획이지 진척이 아니다. 본문을 한 글자라도 고치면 여전히 풀린다. `requirements.md`와
`design.md`는 그대로 엄격하다.

## 상태는 어디에도 저장하지 않는다

2단계와 같다. "어디까지 했나"는 변수에 없다 — **`tasks.md`의 체크 표시가 답**이고, 매번
파싱해서 다시 센다. 그래서 서버가 죽어도, 세션을 새로 열어도, 사람이 손으로 칸을 되돌려도
맞는다. 되돌리기 기능을 따로 만들지 않는다: `- [x]`를 `- [ ]`로 고치면 다음 `/spec-run`이
그 작업을 다시 한다.

**한 가지 예외가 표식이다.** "이 세션은 2.1의 실행이다"는 디스크에 없으므로 세션에 적는다 —
`/spec-run`이 새 세션에 보내는 숨긴 메시지의 `details`에. `agent_settled`가
`ctx.sessionManager.buildContextEntries()`에서 그것을 찾는다.

메모리에 두지 못하는 이유는 확인한 사실이다: `newSession`은 세션을 바꿀 때마다
`createAgentSessionServices`를 새로 부르고, 그것이 `DefaultResourceLoader`를 새로 만들어
`reload()`하므로 **확장 팩토리가 다시 돈다**(`server.ts`의 `createRuntime`). 명령을 처리한
인스턴스와 `agent_settled`를 받는 인스턴스가 다르고, 앞의 것이 적어 둔 값은 뒤의 것에 없다.
표식이 세션에 있으면 앱을 껐다 켜도, 그 세션으로 돌아와도 남는다.

`details`에는 시작할 때 **이미 끝나 있던 작업들**도 함께 넣는다. 끝에서 코드는
`끝나 있던 것 ∪ 이번 작업`으로 칸을 다시 쓰므로, 모델이 남의 칸을 체크해도 무효가 된다.

### `specTasks.ts` (새 파일)

`tasks.md`의 파서. `spec.ts`처럼 Octave의 것이 없어 터미널에서도 돈다.

  `2.1`은 `2`의 하위. Kiro의 "Start task"가 깨진 이슈(#2476·#3810·#9405)가 전부 여기다.
- 나머지 줄(하위 글머리, `_Requirements:_`, 제목)은 조용히 무시한다. 우리 에이전트가 쓴
  파일만 읽으면 되므로 너그럽게 읽지 않는다.
- 다음 작업은 안 끝난 것 중 첫 번째. **하위가 있는 상위는 건너뛴다**(Kiro: "하위부터") —
  상위는 묶음이라 따로 할 일이 없고, 하위가 전부 끝나면 상위도 함께 체크된다.
- 칸을 다시 쓸 때 그 줄의 칸 말고는 한 바이트도 건드리지 않는다.

### `specApproval.ts`

### `spec.ts`

1. **`/spec-run [이름] [번호]`** — `2.1` 모양의 인자는 번호, 나머지는 이름.
   - 에이전트가 일하는 중이면 알리기만 한다(`/spec`과 같음).
   - 세 문서가 다 승인되지 않았으면 무엇이 기다리는지 알린다.
   - 할 작업이 없으면 그렇다고 알린다.
   - **커밋 안 한 변경이 있으면 시작하지 않는다.** 커밋은 폴더 전체를 담으므로, 사람이 하던
     일이 작업의 커밋에 섞이지 않게. 스펙 폴더 아래만 더러운 것은 통과한다 — 세 문서는 첫
     작업의 커밋에 함께 들어간다.
   - 새 세션을 열고, 그 안에 지시문을 숨긴 메시지로, 친 명령을 사람의 메시지로.
2. **실행 지시문** — Kiro 프롬프트의 Task Instructions 그대로: 시작 전에 세 문서를 반드시
   다 읽어라 / 하위 작업이 있으면 하위부터 / 한 번에 작업 하나, 다른 작업의 기능은 만들지
   마라 / 작업에 적힌 요구사항에 비추어 자기 구현을 확인해라 / 끝나면 멈춰라, 다음 작업으로
   알아서 넘어가지 마라. 더해서 우리 것: `tasks.md`를 고치지 마라(끝난 것은 코드가 적는다),
   커밋하지 마라, `.git`을 쓰지 마라.
3. **턴이 끝날 때** — 표식이 있으면: 바뀐 것이 없으면 그렇다고 알리고 끝(체크도 커밋도 없다).
   있으면 칸을 체크하고, 폴더 전체를 담아 커밋 하나를 만들고, 무엇이 끝났고 다음이 무엇인지
   알린다. 커밋 메시지는 **작업 줄 그대로** — 그 줄은 사람이 미리 읽고 승인한, 이 변경의
   정의다. 표식이 없으면 지금 하던 일(브랜치 개명, 기다리는 문서 알림) 그대로.

### 화면은 이번에도 없다 (1c로) — **승인만 붙음(2026-09-20)**

`tasks.md` 위의 "Start task" 단추와 진행 막대는 1c에서 스펙 문서 열기와 같이 한다.
그때까지 `/spec-run`을 메시지 상자에 친다.

모습은 이렇다 — 작업 줄마다 `Start`(와 모델·effort를 고르는 곳), 스펙 어디서나 보이는
진행(몇 번째 / 몇 개 남음), 그리고 끝난 작업 줄 아래 접히는 한 줄: 커밋 해시, 검사 결과,
`[diff] [기록]`. 그 한 줄은 커밋에서 읽는다 — 아래 "정한 것".

## 실모델로 본 것 (2026-09-20, gpt-5.6-luna, thinking minimal)

두 번 돌렸다. 스크립트는 `.context/spec-task-run.mjs`(터미널 `pi --mode rpc -e spec.ts`)와
`.context/spec-task-octave.mjs`(Octave 서버)다. 둘 다 작은 Express 저장소에 `/spec` 한 줄로
시작해 승인 셋을 지나고 `/spec-run`을 두 번 쳤다.

| | 터미널 | Octave |
|---|---|---|
| 세 문서 읽기 | 매번 셋 다 먼저 | 같음 |
| 한 번에 작업 하나 | 지킴, 끝나고 멈춤 | 같음 |
| 커밋 | 작업마다 하나, 메시지는 작업 줄 그대로(한국어) | 같음 |
| 첫 커밋 | 세 문서와 `approvals.json`이 코드와 함께 | 같음 |
| 두 번째 커밋 | 첫 커밋 위에, 자기 것만 | 같음 |
| `tasks.md` | 모델은 건드리지 않음, 칸은 코드가 | 같음 |
| 자기 확인 | `npm test`를 돌려 통과를 보고 | 셸이 없어 못 돌림 — 코드와 테스트를 쓰고 멈춤 |
| 남는 것 | 없음 | `?? .pi/` 그대로(커밋에 안 들어감) |

**테스트가 파랬는데 앱에서는 안 돌던 것 셋.** 전부 실제로 띄워 봐야만 보였다.

1. **`.pi/`가 실행을 막았다.** Octave는 여는 폴더마다 `.pi/`를 쓰고 그 안의 `.gitignore`는
   자기를 못 가려 untracked로 남는다. 폴더가 절대 깨끗해지지 않으니 "더러우면 시작 안 함"에
   매번 걸려, **앱에서는 작업이 한 번도 돌 수 없었다.** 시작했더라도 `git add -A`가 앱의
   파일을 사람의 커밋에 넣었을 것이다. → `.pi/`는 사람의 일이 아니다: 막지도 않고 담지도 않는다.
2. **창이 실행을 보지 못했다.** pi의 `sendUserMessage`는 턴이 끝나야 끝나고, `newSession`은
   그 콜백이 끝나야 돌아온다. 기다리면 서버가 떠나온 세션을 붙든 채 실행 내내 아무것도 듣지
   못하고, 끝난 뒤 완성된 화면으로 툭 바뀐다. → 턴은 시작만 하고 기다리지 않는다.
3. **실행이 사람의 모드를 지나쳤다.** 모드는 서버가 뜰 때와 창의 "새 세션"에서만 적용되고
   있었다. 명령이 여는 세션은 그 길을 지나지 않아 pi의 기본 넷(`read`·`bash`·`edit`·`write`)으로
   열렸다 — 사람이 고른 것이 무엇이든. → 명령이 여는 세션도 사람의 모드로 연다.
   (그때의 기본 모드는 셸이 없는 Coding이었다. 그 뒤 사다리는 Plan·Execution 두 칸이 됐고,
   기본은 셸이 있는 Execution이다 — 아래 "남은 질문"이 그 결정이다.)

첫 터미널 실행에서는 `node_modules` 616개가 커밋에 들어갔다. 그 임시 저장소에 `.gitignore`가
없어서였고(`git add -A`는 무시 목록을 지킨다), 기능이 아니라 실험 장치의 문제였다. 고친 뒤
다시 돌린 기록이 위의 표다.

## 정한 것

- 명령 이름은 `/spec-run`(2026-09-20) — `/spec`·`/spec-approve` 옆에 나란히 보인다.
- 커밋 메시지는 작업 줄 그대로, 본문에 스펙과 번호 한 줄(2026-09-20). → 본문은 트레일러가 됐다(2026-09-21):
  `Spec:`·`Task:`, 그리고 모델이 답 끝에 적은 `Checks:` 줄(지시문이 요구한다; 없으면 `none`).
  `git log --format=%(trailers:key=Checks,valueonly)`로 읽는다. 4단계(결과 읽기)가 읽을 것이 여기 남는다.
- 하위가 전부 끝난 상위 작업도 함께 체크한다(2026-09-20).
- 화면은 1c로 미룬다(2026-09-20). → 승인 쪽은 1c 앞 절반에서 붙었다(PR #24); 작업 쪽은 남았다.
- **결과는 커밋에, 증거는 `.pi/`에**(2026-09-20). 작업이 끝나면 짧은 사실은 커밋 메시지의
  트레일러로 남긴다 — `Spec:`, `Task:`, 그리고 검사를 돌렸다면 `Checks: npm test — 923 passed`.
  git이 `Co-authored-by:`를 담는 자리이고, 클론에도 PR에도 남으며 읽는 법은 `git log` 하나다.
  전체 출력과 스크린샷은 `.pi/runs/{번호}/`에 두고 커밋에는 경로만 남긴다. `git notes`는 쓰지
  않는다(앱 밖에서 보이지 않는데 배관만 는다) — 자세히는 `spec-mode.md` 6절.
- **번호 여럿은 순차 큐다**(2026-09-21). `/spec-run 2.1 2.2 2.3`은 준 순서대로, 작업마다 제 세션에서,
  앞 작업이 **커밋된 뒤에만** 다음을 연다. 병렬이 아니다 — 작업은 앞 작업 위에 쌓이고, 무엇이
  독립인지는 `_After:`가 생기기 전까지 문서에 없다(6번). 바뀐 것이 없거나 커밋이 안 된 작업에서
  큐는 멈추고, 그 뒤는 시작하지 않는다 — 안 한 것을 지나치지 않는다. 이어 가는 자리는 `withSession`이
  준 새 세션의 컨텍스트다: 이벤트 컨텍스트에는 `newSession`이 없고, 명령의 컨텍스트와 그 `pi`는 세션이
  바뀐 순간 stale이다(실제로 그렇게 터졌다). pi의 `sendUserMessage`는 그 세션의 `agent_settled`까지
  기다린 뒤 풀리므로, 그 뒤에 `finishTask`가 모듈에 남긴 결과와 `tasks.md`만 읽고 다음을 연다.
  화면의 "고른 작업들 실행"은 이 명령 한 줄을 보내는 것이다.
- **모델과 effort는 명령의 낱말이다**(2026-09-21). `/spec-run 2.1 faux/cheap low` — 슬래시가 있는 낱말이
  모델(`provider/id`, 피커의 키 그대로), pi의 단계 이름이 effort, 숫자가 작업, 나머지가 스펙 이름.
  큐 전체에 같은 값이 내려간다. 맞추는 자리는 새 세션의 `session_start`: 여는 쪽 인스턴스의 `pi`는
  세션이 바뀐 순간 stale이고 `withSession`의 컨텍스트에는 setter가 없어서, 바람을 모듈에 폴더별로
  남기고 새 인스턴스가 첫 턴 전에 자기 `pi.setModel`·`setThinkingLevel`로 맞춘다. 세션에만 적용되고
  설정에는 남기지 않는다 — 다음에 사람이 여는 세션은 원래 모델로.
- `tasks.md` 파서는 `listEdit`의 lezer 트리를 쓰지 않는다(2026-09-20). 그것은 편집기의 것이라
  브라우저 쪽에만 있고, `spec.ts`는 터미널에서도 돌아야 한다. 우리 에이전트가 쓴 파일만 읽으면
  되므로 줄 단위로 엄격하게 읽는 것으로 충분하다.
