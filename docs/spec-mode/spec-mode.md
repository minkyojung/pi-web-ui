# 스펙 모드 — Octave를 spec-driven 개발 에이전트로

2026-09-18, 0.0.6 공개 직후 사용자와 정한 방향. **코드 없음.** 이 한 장만 읽고 이어갈 수 있게 쓴다.
참고: [`kiro-how-it-works.md`](kiro-how-it-works.md)(Kiro가 순서대로 어떻게 도는가), [공개된 Kiro 스펙 에이전트 프롬프트](https://gist.github.com/notdp/19822831b54190bd9c6b34f6b69fadeb).

## 1. 왜

- 지금 사용자는 전부 개발을 하는 사람들이다.
- 그들이 지금 방식에서 느끼는 한계: **끝없이 반복되는 채팅의 피로**, 그리고 **틀린 계획 때문에 되돌아가는 일**.
- 그래서: 스펙을 철저히 쓰는 데 힘을 더 쓰고, 분명한 계획 아래 실행은 전부 에이전트에게 맡긴다 — Kiro의 방향.

계획이 틀리는 세 가지 경우(사용자 정리) + 하나:
1. 에이전트가 코드베이스를 잘 모른다.
2. 사용자가 목적지까지 가는 데 필요한 지식과 단계를 모른다. 모른다는 것도 모른다.
3. 여러 선택지를 고민해 보지 못했다.
4. (추가) 실행 중에야 드러나는 틀림 — 되돌아갈 길이 없으면 비싸다.

## 2. 전제

**Kiro의 방식은 정답으로 놓는다.** 거기서부터 부정하면 증명할 것이 너무 많다. 증명할 것은 우리가 얹는 차이뿐이다.

Kiro의 몸통은 셋이다 (자세히는 `kiro-how-it-works.md` 10절):
1. 고정된 문서 형식 셋 — `requirements.md` · `design.md` · `tasks.md`
2. "분명한 승인 전에는 다음으로 안 간다"는 상태 기계 — 승인 질문은 전용 도구 호출
3. "세 문서를 읽고, 작업 하나만 하고, 멈춘다"는 실행 규칙

## 3. 최종 지점

> 한 줄을 쓰면, 승인한 스펙대로 에이전트가 끝까지 만들고, 나는 승인만 한다.

- **1차 — 기준선.** Kiro IDE의 몸통 셋이 Octave 안에서 돈다. 더해서 pi 기반이라 어떤 LLM이든 붙는다.
- **2차 — 엣지.** Kiro가 비워 둔 "승인 직전"을 채운다 + 실행을 믿을 만하게 한다.
  - 승인 앞의 되묻기: 에이전트가 코드를 먼저 읽고(경우 1), 사용자가 안 정한 것을 질문지로 묻고(경우 2), 되돌리기 어려운 결정에만 선택지·추천을 붙이고(경우 3), 승인 때는 "당신이 정한 것"만 보게 한다.
  - 고치기는 채팅 재생성이 아니라 문서의 그 자리에서.
  - 실행 중 막히면 재계획이 아니라 멈추고 스펙의 그 문장으로 돌아온다(경우 4).
  - 작업마다 worktree, 앱이 직접 돌리는 검사, 합친 뒤 한 번 더 검사.
  - 검토자는 **다른 회사 모델** — pi라서 되는 것. (여러 LLM은 해자가 아니라 역할 나누기에 쓴다: 스펙=강한 모델, 실행=싼 모델, 검토=다른 눈.)

## 4. 순서

한 단계 = PR 하나 = e2e 하나 = 릴리스 하나.

| # | 만드는 것 | 쓰는 기존 자산 | 끝났다는 증거 |
|---|---|---|---|
| 0 | 준비: main(0.0.6)에서 새 브랜치 + 전용 worktree. typecheck·단위·e2e 전부 초록, 개수 기록(skipped 0까지) | — | 숫자가 이 문서에 적힘 |
| 1 | 뼈대: `.git` 있는 폴더에서 "새 스펙" → 한 줄 → `requirements.md`가 써져 탭에 열림. 스펙 폴더는 일반 write로(guard를 그 범위만 풂) | `prompts.ts`, 탭 | e2e |
| 2 | 승인 관문 셋: 승인 질문은 전용 도구 호출 → 메시지 상자 자리에 승인/고쳐 달라. 단계 상태 = 어떤 파일이 있는가(별도 저장소 없음) | ask_user 도구 + 질문지 UI | 세 문서가 차례로 생기고, 승인 없이는 다음으로 못 감 |

| 4 | diff 보기: 작업이 바꾼 파일을 읽기 전용으로 | — | e2e |
| 5 | **Octave로 Octave를 만든다** — 6번 기능 하나를 스펙 모드로 | — | 계속할지 본다 |
| 6~ | 엣지: 체크포인트/worktree → 앱이 돌리는 검사 → 되묻기 → 다른 모델 검토 → Run all. 맨 마지막에 `history.ts` 삭제 | | |

## 5. 규칙

- **5번 전에는 엣지를 만들지 않는다.** 기준선이 통하는지가 먼저다.
- **5번 전에는 아무것도 지우지 않는다.** 삭제는 방향이 확인된 뒤.
- 스펙 기능은 **열린 폴더에 `.git`이 있을 때만** 나타난다. main에서 계속 릴리스해도 지금 테스터의 노트 앱은 그대로다. 오래 사는 분기를 만들지 않는다.
- 문서 형식·프롬프트는 공개된 Kiro 프롬프트에서 출발한다. 우리 파서는 우리 에이전트가 쓴 파일만 읽으면 된다 — Kiro 파일과의 호환은 필요해질 때.
- 단계마다 단위·e2e 개수가 0번의 숫자에서 줄지 않는다.
- 새 작업은 전용 worktree에서. `brussels`는 다른 에이전트와 같이 쓰는 폴더다.

## 6. 정한 것

- **모드를 나누지 않는다.** 노트 모드/코드 모드 전환 없음. 코드 기능은 `.git`이 있으면 저절로.
- **"누가 썼는지" 기록은 포기한다.** 내세우지 않고, 새 기능을 그 위에 설계하지 않는다. 코드·스펙의 되돌리기는 git(나중에 턴 단위 체크포인트 — Cline·Claude Code식 그림자 저장소)이 맡는다. `history.ts`와 표시 코드는 6번 이후에 지운다. 충돌 거절은 기록이 아니라 편집기의 버전 동기화가 하는 일이라 남는다.
- **노트 기능(PDF·수식·임베드·속성 …)은 얼린다.** 지우지 않고, 더 투자하지 않는다.
- 편집기와 제안/Keep은 걷어내지 않는다 — 스펙 문서를 사람과 에이전트가 같이 고치는 통로이고, 2차 엣지의 바탕이다. 다만 1차에서 스펙 문서는 일반 write로 바로 쓴다.
- Kiro를 직접 돌려 보는 일은 생략한다. 공개된 프롬프트에 형식과 예시가 있다.
- 코드 편집기·터미널 창은 만들지 않는다.

## 7. 열린 것

1. 스펙 폴더의 자리 — `.kiro/specs/{이름}/` 그대로인가, 우리 이름(`.octave/specs/`, `specs/`)인가.
2. guard를 어디까지 푸는가 — 스펙 폴더만인가, `.git` 있는 폴더 전체의 `.md`인가.
3. README 첫 줄과 시스템 프롬프트(`guard.ts`의 "You are not their programmer")를 언제 바꾸는가 — 5번을 지난 뒤가 자연스럽다.
4. Requirements-first만인가, design-first·bugfix·Quick Spec도 1차에 넣는가 — 추천: requirements-first 하나만.
5. steering(`product.md`·`tech.md`·`structure.md`)에 해당하는 것 — 추천: 이미 읽는 `AGENTS.md`/`CLAUDE.md`로 충분, 1차에는 없음.
