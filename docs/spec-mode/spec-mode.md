# 스펙 모드 — Octave를 spec-driven 개발 에이전트로

2026-09-18, 0.0.6 공개 직후 사용자와 정한 방향. **코드 없음.** 이 한 장만 읽고 이어갈 수 있게 쓴다.
참고: [`kiro-how-it-works.md`](kiro-how-it-works.md)(Kiro가 순서대로 어떻게 도는가), [공개된 Kiro 스펙 에이전트 프롬프트](https://gist.github.com/notdp/19822831b54190bd9c6b34f6b69fadeb).

## 1. 왜

- 지금 사용자는 전부 개발을 하는 사람들이다.
- 그들이 지금 방식에서 느끼는 한계: **끝없이 반복되는 채팅의 피로**, 그리고 **틀린 계획 때문에 되돌아가는 일**.
- 그래서: 스펙을 철저히 쓰는 데 힘을 더 쓰고, 분명한 계획 아래 실행은 전부 에이전트에게 맡긴다 — Kiro의 방향.

계획이 틀리는 세 가지 경우(사용자 정리) + 하나:
1. 에이전트가 코드베이스를 잘 모른다.
2. 사용자가 목적지까지 가는 데 필요한 지식과 단계를 모른다. 모른다는 것도 모른다.
3. 여러 선택지를 고민해 보지 못했다.
4. (추가) 실행 중에야 드러나는 틀림 — 되돌아갈 길이 없으면 비싸다.

## 2. 전제

**Kiro의 방식은 정답으로 놓는다.** 거기서부터 부정하면 증명할 것이 너무 많다. 증명할 것은 우리가 얹는 차이뿐이다.

Kiro의 몸통은 셋이다 (자세히는 `kiro-how-it-works.md` 10절):
1. 고정된 문서 형식 셋 — `requirements.md` · `design.md` · `tasks.md`
2. "분명한 승인 전에는 다음으로 안 간다"는 상태 기계 — 승인 질문은 전용 도구 호출
3. "세 문서를 읽고, 작업 하나만 하고, 멈춘다"는 실행 규칙

## 3. 최종 지점

> 한 줄을 쓰면, 승인한 스펙대로 에이전트가 끝까지 만들고, 나는 승인만 한다.

어떻게 도는가 (2026-09-18 정함 — 단위는 **스펙 하나 = 브랜치 하나 = worktree 하나 = PR 하나, 작업 하나 = 커밋 하나**):

1. 사용자가 저장소 폴더를 Octave로 연다(main이든 무엇이든).
2. 사이드바의 +가 모달을 연다(2026-09-20 정함): 저장소 이름, "무엇을 만들까요?" 한 줄, 그리고 이 스펙을 맡을 모델과 effort. Create 하나가 worktree를 만들고 **그 자리에서 요구사항 턴을 시작한다** — 친 한 줄이 `/spec`의 한 줄이다. 워크트리는 이 문으로만 생긴다: 빈 워크스페이스를 만드는 길은 없고, 잡담은 이미 있는 워크스페이스에서 한다.
3. worktree는 도시 이름 브랜치로 먼저 난다. 에이전트가 이름을 짓고(`email-auth`) 첫 문서를 쓰면, 그 턴이 끝날 때 코드가 git으로 브랜치 이름을 `{사용자}/email-auth`로 바꾼다 — 폴더 이름은 그대로(1b). 원래 폴더와 main은 PR이 합쳐질 때까지 아무것도 모른다.
4. 그 안에서 세 단계: `requirements.md` → 승인 → `design.md` → 승인 → `tasks.md` → 승인. `.octave/specs/email-auth/`에. 문서는 따로 커밋하지 않고 첫 작업 커밋에 코드와 함께 들어간다(Kiro와 같음).
5. "Start task": 새 세션이 세 문서를 읽고 작업 하나를 하고 스스로 확인한 뒤 멈춘다 → 커밋 하나 → 체크. 맡길 때 그 작업의 모델과 effort를 고를 수 있고(스펙은 강한 모델, 실행은 싼 모델), 무엇이 끝났는지는 커밋에 한 줄로 남는다(6절 "결과는 커밋에"). (앱이 직접 돌리는 검사는 1차에 없다 — 2차 엣지.) 다음 작업도 같은 브랜치 위에서 — 작업은 앞 작업 위에 쌓이므로 작업마다 worktree를 나누지 않는다.
6. 전부 끝나면 PR. 스펙 세 문서와 코드가 함께 담긴다.
7. 합친 뒤 worktree를 정리한다.

출처: 2·4·5번(한 줄, 세 문서와 승인, 작업 하나 하고 멈춤)은 Kiro IDE, 스펙마다 브랜치+worktree와 작업마다 커밋은 Kiro Crew Task Runner, PR은 Kiro 자율 에이전트 — 셋 다 Kiro의 방식을 이어 붙인 것이다.

사람이 하는 일은 한 줄, 승인 세 번, 마지막 PR 확인이다. 이 흐름은 "새 스펙"을 누를 때만 시작된다 — 작은 일과 묻는 일을 위한 지금의 대화는 그대로 있다.

- **1차 — 기준선.** Kiro IDE의 몸통 셋이 위의 그릇 안에서 돈다. 더해서 pi 기반이라 어떤 LLM이든 붙는다.
- **2차 — 엣지.** Kiro가 비워 둔 "승인 직전"을 채운다 + 실행을 믿을 만하게 한다.
  - 승인 앞의 되묻기: 에이전트가 코드를 먼저 읽고(경우 1), 사용자가 안 정한 것을 질문지로 묻고(경우 2), 되돌리기 어려운 결정에만 선택지·추천을 붙이고(경우 3), 승인 때는 "당신이 정한 것"만 보게 한다.
  - 고치기는 채팅 재생성이 아니라 문서의 그 자리에서.
  - 실행 중 막히면 재계획이 아니라 멈추고 스펙의 그 문장으로 돌아온다(경우 4).
  - 턴 단위 체크포인트, 앱이 직접 돌리는 검사, 합친 뒤 한 번 더 검사. 서로 독립인 작업을 동시에 돌릴 때(Run all)에만 작업별 worktree.
  - 검토자는 **다른 회사 모델** — pi라서 되는 것. (여러 LLM은 해자가 아니라 역할 나누기에 쓴다: 스펙=강한 모델, 실행=싼 모델, 검토=다른 눈.)

## 5. 규칙

- **5번 전에는 엣지를 만들지 않는다.** 기준선이 통하는지가 먼저다.
- **5번 전에는 아무것도 지우지 않는다.** 삭제는 방향이 확인된 뒤.
- **Octave는 코딩 에이전트로 갈아탄다**(2026-09-18, 사용자 결정): 여는 것은 git 저장소뿐이고, 노트 폴더는 열리지 않아도 된다. 노트 기능의 코드는 5번까지 지우지 않는다 — 열 수 없을 뿐이다. 오래 사는 분기를 만들지 않는다.
- 문서 형식·프롬프트는 공개된 Kiro 프롬프트에서 출발한다. 우리 파서는 우리 에이전트가 쓴 파일만 읽으면 된다 — Kiro 파일과의 호환은 필요해질 때.
- 단계마다 CI 초록, 로컬 skipped 0(1Password가 잠기면 서버 테스트가 조용히 건너뛴다). 준비 단계(0번)는 두지 않는다 — 이 worktree가 이미 main에서 갈라진 전용 브랜치이고 main CI가 초록이다(2026-09-18).
- 새 작업은 전용 worktree에서. `brussels`는 다른 에이전트와 같이 쓰는 폴더다.

## 6. 정한 것

- **모드를 나누지 않는다.** 노트 모드/코드 모드 전환 없음. 코드 기능은 `.git`이 있으면 저절로.
- **"누가 썼는지" 기록은 포기한다.** 내세우지 않고, 새 기능을 그 위에 설계하지 않는다. 코드·스펙의 되돌리기는 git(나중에 턴 단위 체크포인트 — Cline·Claude Code식 그림자 저장소)이 맡는다. `history.ts`와 표시 코드는 6번 이후에 지운다. 충돌 거절은 기록이 아니라 편집기의 버전 동기화가 하는 일이라 남는다.
- **노트 기능(PDF·수식·임베드·속성 …)은 얼린다.** 지우지 않고, 더 투자하지 않는다.
- 편집기와 제안/Keep은 걷어내지 않는다 — 스펙 문서를 사람과 에이전트가 같이 고치는 통로이고, 2차 엣지의 바탕이다. 다만 1차에서 스펙 문서는 일반 write로 바로 쓴다.
- Kiro를 직접 돌려 보는 일은 생략한다. 공개된 프롬프트에 형식과 예시가 있다.
- 코드 편집기·터미널 창은 만들지 않는다.
- **스펙 폴더는 `.octave/specs/{이름}/`.** (2026-09-18) Kiro가 점 폴더를 쓰는 이유는 우리에게도 그대로다: 남의 저장소에 손님으로 들어가므로 `spec/`·`specs/`(RSpec 등 테스트 폴더의 이름)와 부딪치지 않아야 하고, glob·린터·문서 빌드·ripgrep이 점 폴더를 기본으로 건너뛰어 스펙이 사용자의 도구와 에이전트의 코드 검색에 섞이지 않으며, 도구의 것이 한 뿌리 아래 모여 git에 올라간다. `.kiro/`가 아닌 것은 그것이 Kiro의 폴더라서다 — 같이 쓰는 사람의 파일을 덮어쓴다. 호환은 필요해질 때 읽는 경로로 더한다. `.pi/` 아래가 아닌 것은 거기가 잠긴 앱의 영역이고 git에 올리는 곳이 아니라서다.
- **스펙 문서는 노트가 아니라 세 번째 파일 종류다.** (2026-09-18) 탭에 열리고 트리에 보이고 디스크의 변경을 따라오고 사람도 고치지만, 저자 기록·note_edit 강제·링크/속성 인덱스·노트 검색에는 들어가지 않는다. 자리는 이미 있다 — `documentKinds.ts`의 "document"(지금은 PDF)와 `vault.ts`의 `documentAt`; 스펙 문서는 그 종류의 편집 가능한 구성원이다. 경로 판정은 전부 `vault.ts`의 `fileAt`을 지나므로 "이 경로 아래의 `.md`는 스펙"이라는 판정 하나를 더하고, 노트 쪽 코드는 지금처럼 점 폴더를 못 보는 채로 둔다 — 노트에서 빼내는 예외를 만들지 않는다.
- **단위: 스펙 = 브랜치 = worktree = PR, 작업 = 커밋.** (2026-09-18) main에 스펙을 쓰지 않는다. 기능 하나 = 브랜치 하나 = PR 하나가 개발의 표준 단위이고, GitHub Spec Kit(`/specify`가 브랜치를 만들고 거기에 스펙을 쓴다)과 Conductor(워크스페이스 = worktree = 브랜치 = PR)가 그렇게 한다. 같은 폴더에서 브랜치를 바꾸지 않고 worktree인 것은 사용자가 하던 일과 꼬이지 않고, 에이전트가 만드는 동안 사용자가 자기 폴더에서 다른 일을 할 수 있어야 해서다. 작업마다 worktree를 나누지 않는 것은 작업이 앞 작업 위에 쌓이기 때문이다(Kiro 프롬프트: "앞 단계 위에 쌓고, 마지막은 전부 잇는다") — 나누면 매번 합쳐야 한다. 작업이 커밋이면 틀린 작업은 그 커밋만 되돌리고, diff 보기는 그 커밋의 diff다.
- **자리는 Conductor와 같다** — GitHub에서 받은 원본 클론은 `~/octave/repos/{저장소}`(Conductor에도 `~/conductor/repos`가 있다; `workspaces`라는 이름의 저장소와 부딪치지 않게), 로컬에서 연 저장소는 제자리, 워크스페이스는 `~/octave/workspaces/{저장소}/{도시}`(보이는 폴더: 사람이 Finder·터미널·편집기로 연다; `~/.octave`는 로그 같은 앱 데이터로 남는다). 원본에서는 일하지 않고 목록에도 없다. 새 워크스페이스는 `origin`을 fetch한 뒤 기본 브랜치(`origin/HEAD`)에서, 브랜치 이름 `{GitHub 사용자}/{도시}`로 갈라낸다 — 원본의 브랜치는 움직이지 않는다. **폴더 이름은 바꾸지 않는다**: pi가 대화를 폴더 경로로 저장하므로 옮기면 대화가 사라진다. 바뀌는 것은 브랜치 이름과 화면의 제목뿐(1b).
- **폴더마다 서버 하나, Electron이 관리자**(2026-09-18). Conductor가 워크스페이스마다 에이전트 프로세스를 하나 두는 것과 같고(셸의 작업 폴더는 `/`, 에이전트만 워크스페이스에 — 확인함), 서버의 고정된 `CWD`를 건드리지 않는다. 한 서버가 여러 폴더를 맡으면 한 스레드를 나눠 써 서로를 막는다. 전환은 창을 그 폴더의 서버로 다시 불러오는 것이고 뒤의 서버는 계속 돈다 — 폴더마다 페이지를 따로 두면 메뉴의 새로고침·개발자 도구·확대와 창을 끄는 영역이 빈 바탕에 걸린다. 안 쓰는 서버는 멈춘다.
- **GitHub는 `gh`로**(2026-09-18). Conductor처럼 사용자가 이미 한 로그인을 쓰고, 토큰을 저장하지 않는다. `gh`가 없어도 로컬 저장소 열기·worktree·fetch는 git만으로 되고, URL을 붙여 넣으면 `git clone`으로 받는다. OAuth(Cursor는 VS Code의 내장 GitHub 로그인)는 `gh` 없는 사람이 막히거나 PR 기능이 필요할 때 — GitHub를 부르는 것은 한 모듈에 모아 두어 그 안만 바꾸면 되게 한다.
- **그릇은 하나, 첫 문서가 종류다.** 브랜치 → worktree → 승인 관문 → 작업 = 커밋 → PR은 기능·버그·리팩토링에 똑같다. 다른 것은 첫 문서뿐이다(Kiro: `requirements.md` / 설계 먼저 / `bugfix.md` / Quick Spec). **1차는 requirements-first 하나.** 종류를 더하는 것은 프롬프트와 문서 형식 하나를 더하는 일이고, 무엇이 먼저 아쉬운지는 5번에서 드러난다(예상: 버그). 리팩토링은 Kiro에도 전용 종류가 없다 — 설계 먼저 + 버그 스펙의 "그대로여야 하는 동작" 칸의 조합이다.
- **자물쇠는 체크포인트와 함께 걷어낸다.** (2026-09-18) 다른 코딩 에이전트(Claude Code, Codex, Cline, Cursor, Kiro, Conductor)는 파일 종류로 쓰기를 막지 않는다 — 폴더에 가두고, 되돌릴 수 있게 하고, 필요하면 묻는다. guard의 노트 규칙과 wall이 `.md`를 막은 이유는 저자 기록 하나였고 그 기록은 포기했으므로, 갈 곳은 "막지 않는다"이다. 그러나 지금 에이전트의 쓰기를 되돌리는 것은 `history.ts`와 턴 되돌리기뿐이고 그것은 note_edit을 거친 쓰기만 안다 — 체크포인트 없이 먼저 풀면 되돌릴 수 없는 쓰기가 생긴다. 그래서 6번의 체크포인트 PR까지 미뤄 두었다.
  **앞당겨 걷어냄(2026-09-20).** 3번이 끝나면서 되돌릴 수단이 생겼기 때문이다 — 작업 하나가 커밋 하나이므로 실행이 쓴 것은 `git revert` 하나로 돌아가고, 그전에 diff로 읽을 수 있다. 그리고 미룬 대가가 5번을 막고 있었다: 이 저장소는 사람이 보는 변화마다 `CHANGELOG` 한 줄을 같은 커밋에 넣으므로, 작업 실행이 첫 커밋부터 막힌다. 그래서 guard의 노트 규칙을 없애고 wall에서 `.md` 금지(와 그것에 내던 `.octave/` 구멍)를 걷어냈다. **남는 것은 `.pi/` 보호 하나**다 — 셸이 무엇을 쓸지는 명령을 읽어 알 수 없으므로 커널이 막는다. 사람이 치고 있는 글은 편집기가 지킨다(`noteSync.ts`가 '보여 줄 것'과 '충돌'을 가린다 — 셸과 다른 편집기를 위해 이미 있던 길이고, 에이전트가 거기 한 명 더 들어온 것뿐이다). `note_edit`·`note_write`·`note_properties`는 등록된 채 남지만 강제하지 않는다.
- **워크트리는 모달로만 생긴다.** (2026-09-20) 사이드바의 +는 "새 폴더"가 아니라 **스펙을 시작하는 문**이다: 저장소, 한 줄, 모델과 effort, Create. 친 한 줄이 `/spec`의 한 줄이고, Create 하나가 worktree를 만들고 첫 턴을 시작한다 — 만들기와 시작하기가 갈라져 있으면 사람이 그 사이에서 무엇을 쳐야 하는지 알아야 한다. 빈 워크스페이스를 만드는 길은 두지 않는다: 스펙이 아닌 이야기는 이미 열려 있는 워크스페이스에서 하면 되고, 문이 둘이면 "그래서 어느 쪽?"이 첫 화면의 질문이 된다. Conductor의 새 워크스페이스 상자가 같은 모양이다.
- **작업 실행의 기본은 쌓기다.** (2026-09-20) 작업 하나가 앞 작업의 결과가 있는 폴더에서 시작하므로 이어지는 코드가 자연스럽고, 합칠 일이 없고, 틀린 작업은 그 커밋만 되돌린다. 작업별 브랜치(그리고 동시 실행)는 **서로 독립이라는 것이 문서에 적힌 뒤**의 선택지다 — 그 표시가 `_After:`이고, 그때까지는 무엇이 독립인지 아무도 모른다. 나눠 돌리면 앞 작업의 결과를 못 보므로 같은 파일에서 부딪치거나 서로 모르는 중복이 생기고, 끝나면 합치는 일이 사람에게 남는다.
- **결과는 커밋에, 증거는 `.pi/`에.** (2026-09-20) 작업 하나가 끝나면 남길 것이 둘이다. 짧은 사실 — 무엇을 했고 검사가 통과했는지 — 은 커밋 메시지의 트레일러로(`Spec:`, `Task:`, `Checks: npm test — 923 passed`), git이 원래 `Co-authored-by:`를 담는 그 자리에. 커밋과 한 몸이라 클론에도 PR에도 남고, 읽는 법은 `git log` 하나다. 무거운 증거 — 전체 출력, 스크린샷 — 은 `.pi/runs/{번호}/`에 두고 커밋에는 경로만 남긴다: 저장소를 더럽히지 않는 대신 그 기계에만 있다. **`git notes`는 쓰지 않는다** — 커밋을 건드리지 않고 길게 쓸 수 있지만 기본으로는 push도 fetch도 되지 않고 GitHub에도 보이지 않아, 앱 밖에서 안 보이는데 배관만 느는 쪽이다. 팀이 결과를 나눠 봐야 할 때 다시 꺼낸다.
- **작업 문서에 ProseMirror식 편집기를 쓰지 않는다.** (2026-09-20) `tasks.md`는 터미널의 `pi`도 읽는 엄격한 텍스트이고(`specTasks.ts`가 줄 단위로 읽는다), 승인의 지문이 그 글자에 걸려 있다 — WYSIWYG가 마크다운을 왕복하며 한 글자만 바꿔도 파서와 승인이 함께 깨진다. 작업 줄의 단추, 출처 칩, 의존성 선은 전부 CodeMirror의 위젯과 데코레이션으로 되는 일이고(라이브 프리뷰·임베드·각주가 이미 그 방식이다), VS Code의 CodeLens가 앉는 자리도 거기다. 문서가 아니라 보드로 보고 싶어지면 그것은 편집기가 아니라 `tasks.md`를 읽는 다른 화면이다.
- steering은 1차에 없다 — 이미 읽는 `AGENTS.md`/`CLAUDE.md`로 충분.
- **`/spec`이 보이는 모습**(2026-09-19): 친 한 줄만 사람의 메시지로 남고, 지시문은 같은 턴에 모델에게만 가는 숨긴 메시지다(pi의 `deliverAs: "nextTurn"`) — Claude Code가 명령을 보여 주는 방식. 기다림 없이 바로 시작한다. 지시문은 공개된 Kiro 프롬프트의 requirements 형식 그대로이고, 문서는 사람이 쓴 언어로 쓴다(WHEN·IF·THEN·SHALL은 영어로, 양식의 자리에).
- **판단은 모델이, 조작은 코드가**(2026-09-19): 모델은 이름을 짓고 문서를 쓴다. 브랜치 이름은 `spec.ts`가 그 턴이 끝날 때 git으로 바꾼다 — GitHub Spec Kit도 브랜치는 모델이 아니라 스크립트가 만든다. 실모델 1회차에서, 셸이 없는 모드의 모델이 `git branch -m` 대신 `.git/HEAD`와 ref를 손으로 써서 옛 브랜치가 남고 git 기록이 없었던 것을 보고 정했다. 같은 이유로 guard는 edit·write가 `.git` 안을 쓰는 것을 거절한다(Codex도 쓰기를 허용한 폴더 안의 `.git`을 읽기 전용으로 둔다); 셸의 git은 그대로. 이름은 브랜치가 아직 도시 이름일 때만 바꾼다 — `main`이나 이미 이름이 있는 브랜치는 두 번째 `/spec`에도 그대로.
- **도구 모드는 Plan과 Execution 둘뿐**(2026-09-20). 셸 없이 파일만 고칠 수 있던 중간 칸(Coding)을 없애고, 기본을 셸이 있는 Execution으로 했다. 그 칸은 Octave가 노트 앱일 때의 선이었다 — 코딩 에이전트에서는, 방금 쓴 테스트를 돌려 보지 못하는 작업 실행이 "됐다"고 커밋하는 것이 3번에서 실제로 나온 문제였고, 실모델 기록에서도 셸이 있는 쪽만 자기 작업을 확인했다. Plan은 저장소를 고치기 전에 묻기 위해 그대로 남는다. 물어보는 계층이 없는 것은 여전하므로(`toolModes.ts`), 잘못된 실행을 되돌리는 것은 작업마다의 커밋과 6번의 체크포인트가 맡는다 — "자물쇠는 체크포인트와 함께"의 같은 줄 위에 있다.
- **작업 하나 = 세션 하나 = 커밋 하나, 그리고 뒤의 둘은 코드가 만든다**(2026-09-20). 모델은 세 문서를 읽고 작업 하나를 하고 멈추기만 한다 — Kiro의 실행 규칙 그대로. 칸을 체크하는 것도 커밋하는 것도 `spec.ts`다: 작업이 커밋으로 남는지가 사람이 어느 모드에 있느냐에 달리면 그건 단위가 아니고, 칸과 커밋이 어긋나면 나중에 어느 쪽이 맞는지 가릴 길이 없다. 작업마다 새 세션인 것은 Kiro의 "Start task"와 같다 — 열두 작업을 한 대화에서 하면 문맥이 넘친다. 그래서 명령이 알아낸 것을 담을 데가 없는데(`newSession`이 확장을 통째로 다시 만들어, 명령을 처리한 인스턴스와 턴이 끝나는 인스턴스가 다르다) 표식은 새 세션의 숨긴 메시지에 실어 보내고 턴 끝에 세션에서 도로 읽는다. 자세히는 [`task-runs.md`](task-runs.md).
- **승인은 묻지 않고 사람이 한다**(2026-09-19). Kiro는 모델이 문서를 고칠 때마다 `userInput` 도구로 묻고, 사용자의 답이 승인인지 모델이 가린다. 우리는 묻지 않는다: 질문 창은 메시지 상자 자리에 떠서 더 다듬고 싶은 사람을 방해하고, 모델이 가리는 승인은 샌다. 승인은 사람이 치는 명령(`/spec-approve`)이고, 코드가 기록하고(`approvals.json`에 승인한 문서와 앞 문서들의 지문), 코드가 순서를 지킨다(승인 전 다음 문서의 edit·write 거절). **되돌아가기는 새 장치가 아니다**: 문서가 바뀌면 지문이 달라져 그 문서와 뒤 문서의 승인이 저절로 풀리고, 다시 승인하면 에이전트가 다음 문서를 새 내용에 맞춰 점검한다 — Kiro의 Refine/Sync Files를 사람이 누르지 않아도 되게. 자세히는 `approval-gates.md`.
